# Dev Pipeline -- Queue page search does nothing (non-functional filter)
**Issue:** #119
**PR:** (filled in Phase 3)
**Started:** 2026-03-28

## Phase 1: Problem Statement

**Problem:** The Queue page sidebar "Search" tab is non-functional because:
1. The search API may not return results (endpoint unknown state)
2. `openCaseView(item.applicantName)` passes a display-name string as `personKey` -- fragile and breaks on name mismatches or "(unknown)"
3. No differentiation between "not yet searched" and "no results" empty states
4. Queue-level filter placeholder doesn't communicate it's local-only (not historical search)

**Outcome:** Users cannot search for historical cases via the sidebar search. When they submit a query, either nothing happens or navigation fails silently.

**Acceptance Criteria (from issue):**
- [ ] Submitting a search query in the sidebar Search tab returns matching results from the API
- [ ] Clicking a result opens the case detail correctly using a stable ID (not applicant name string)
- [ ] If search is unavailable, a clear message is shown: "Search is not available -- contact your administrator"
- [ ] Queue-level filter input communicates it only filters current pending queue
- [ ] Error states from the search API are surfaced to the user

## Phase 2: Solution Space

**Candidates considered:**

1. **Band-aid (selected)**: Change `openCaseView(item.applicantName)` to `setSelectedReviewId(item.intakeId)` -- direct doc navigation using the stable UUID already in the search result. Add `onOpenCaseView` to ReviewDetailProps to keep the case aggregate feature accessible from the review detail header.

2. **Local optimum (rejected)**: Keep `openCaseView` but guard against "(unknown)" name. Still fragile for name mismatches, still navigates to case aggregate instead of specific doc.

3. **Redesign (out of scope)**: Rework the `/cases/{personKey}` endpoint to accept a document ID. Would require API changes and is a larger change than needed.

**Selected:** Option 1 -- band-aid. The `intakeId` is already in the search result; the fix is 4 lines. The case aggregate view is kept accessible via a button in the review detail header.
